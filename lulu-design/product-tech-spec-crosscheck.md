# Product-Design 交叉检测框架（SDCA）

## 框架概述

SDCA（Spec-Design Coverage Audit）用于检测「产品规格说明书」和「技术设计文档」之间的覆盖关系，回答两个核心问题：

- **遗漏（GAP）**：Spec 要求了，Design 没有覆盖
- **超出（GHOST）**：Design 决策了，Spec 没有要求

检测分三个方向，建议按顺序执行。

---

## 检测方向 A：覆盖性检测（Spec → Design）

> 核心问题：每一条 Spec 需求，在 Design 里找得到对应的技术设计吗？

### 执行方法

1. 将 Spec 分解为最小需求单元（每条功能、每个边界值、每种错误处理场景）
2. 对每个单元，在 Design 里定位到覆盖它的接口设计 / 数据流 / 模块划分 / 边界条件
3. 找不到对应设计决策的单元，记为 **GAP**

### 需求单元分类

| 类型 | 示例 |
|------|------|
| 正常路径功能 | 「点击 emoji 后分数滑块同步」 |
| 边界值 | 「tooltip 触发半径 ≤20px」 |
| 错误处理 | 「localStorage 解析失败显示提示」 |
| 视觉/交互约束 | 「成功提示 1.5s 后消失」 |
| 数据格式 | 「date 字段格式为 YYYY-MM-DD」 |

### 输出格式

```
GAP-N（严重度：高/中/低）
  Spec 来源：§X.X 第N条
  需求内容：...
  设计现状：（找不到 / 部分覆盖 / 描述不一致）
  建议修复：...
```

### 严重度判断

| 严重度 | 判断标准 |
|--------|---------|
| 高 | 核心功能缺失；不修复会导致实现偏离用户需求或架构决策错误 |
| 中 | 非核心但影响体验；设计遗漏会在编码阶段引发返工 |
| 低 | 边缘情况或提示文案；影响完整性但不阻塞主流程 |

## 检测方向 B：溯源性检测（Design → Spec）

> 核心问题：每一个 Design 决策的产出，在 Spec 里找得到来源吗？

### 执行方法

1. 遍历 Design 每个模块/接口/数据结构的设计决策
2. 对每个决策，找到它在 Spec 中的来源需求
3. 找不到来源的决策，记为 **GHOST（幽灵设计）**

### 判断标准

- **合理扩展**（不记录）：技术基础设施、错误边界兜底、通用性设计，虽不在 Spec 里，属合理技术决策
- **幽灵设计**（记录）：业务功能或行为层面的设计决策，Spec 明确没有要求或列入 Out of Scope

### 输出格式

```
GHOST-N
  Design 来源：§X.X 接口名/模块名
  设计内容：...
  Spec 状态：（未提及 / 明确排除）
  建议处理：删除 / 移入 Out of Scope / 补写 Spec
```

## 检测方向 C：语义一致性检测

> 核心问题：同一概念在 Spec 和 Design 中的描述是否吻合？

检测以下三类偏差：

### C1. 数值偏差

Spec 写了具体数值，Design 使用不同数值。

示例：
- Spec：「tooltip 触发半径 ≤20px（桌面端）」
- Design：接口定义 `radius: 25px` → 数值不符

### C2. 行为偏差

Spec 描述了一种行为逻辑，Design 决定了不同逻辑。

示例：
- Spec：「连续打卡天数从昨天往前数，今天已打卡则 +1」
- Design：从今天往前数（逻辑不同）

### C3. 命名偏差

Spec 中的术语，Design 里用了不同名称（可能导致沟通混乱）。

示例：
- Spec 称「修改模式」，Design 接口叫「editMode」或「updateMode」（可接受差异，但应记录）

---

## 执行建议

1. **先做方向 A**，找出所有 GAP 后再做 B，最后做 C
2. 高严重度 GAP 必须在编码前修复（在设计阶段关闭）
3. GHOST 功能须与产品确认：是补写 Spec 还是删除设计
4. 语义偏差中的数值偏差优先级最高，行为偏差次之，命名偏差可保留记录

---

## 覆盖率指标

```
需求覆盖率 = 已覆盖需求单元数 / Spec 总需求单元数 × 100%
目标：100%（编码前所有 GAP 必须关闭）

溯源率 = 有 Spec 来源的 Design 决策数 / Design 总决策数 × 100%
目标：≥ 95%（允许少量合理技术基础设施）
```

## 与产品文档评估框架的关系

| 维度 | 产品文档评估框架（PDQA）| Spec-Design 交叉检测（SDCA）|
|------|----------------------|--------------------------|
| 检测对象 | 单份规格说明书 | 规格 × 设计 两份文档 |
| 核心问题 | 「文档写得好不好」 | 「两份文档说的是同一件事吗」 |
| 执行时机 | 规格说明书写完后，设计写之前 | 设计写完后，计划开始前 |
| 输出 | 11 维度问题列表 | GAP + GHOST + 语义偏差列表 |
| 修复对象 | 规格说明书本身 | 规格或设计（视 GAP 方向）|

建议执行顺序：

```
写 Spec → PDQA（规格内部质量）→ 写 Design → SDCA（规格×设计对齐）→ 写 Plan → 编码
```
